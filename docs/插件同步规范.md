# 插件同步到 Jack-kd/dsh-plugins 仓库 · 规范

> **怎么用**：以后要「更新插件」或「上传新插件」时，在需求最后加一句——
> **「把插件同步到我的仓库，同步规范看 docs/插件同步规范.md」**
> 然后按下方「可粘贴提示词」整段发给 AI 即可一次到位。

---

## 一、仓库惯例（monorepo）

```
dsh-plugins/
├── package.json          ← 仓库元信息（不是插件，不要动）
├── pnpm-workspace.yaml
├── README.md             ← 安装速查（别人复制链接的地方，必须同步更新；每个插件是一条带版本号徽章的 <details> 折叠块）
└── plugins/
    └── <插件名>/
        ├── package.json        # 含 dsh.bundle.patch 和（如有界面）dsh.client
        ├── cordis.patch.yml    # Loader 补丁，插入插件行
        ├── index.js            # Host（服务端）半部
        ├── client.js           # （可选）客户端半部
        └── locale/ icon.svg    # （可选）
```

- 分发：插件目录打成**内容在根**的 tgz（npm 风格，顶层 `package/`），命名 `<插件名>-plugin.tgz`，传到仓库 **Releases**。
- 安装地址固定格式：`https://github.com/Jack-kd/dsh-plugins/releases/download/<插件名>-v<版本>/<插件名>-plugin.tgz`。
- 安装方式：`dsh plugin --profile web add <URL>`，或「插件管理 → 添加插件 → 粘贴 URL」。
- 升级提示：**当前版本安装后不自动更新，升级需先卸载再装新版本**（写进 README）。

### ⚠️ Tag 命名：必须带插件名前缀

**GitHub 的 tag 在同一个仓库里全局唯一**——这是平台硬限制，没有开关。本仓库是 monorepo，若 tag 只写 `v<版本>`，两个插件版本号相同就会**互相顶号**：

```
gh-accel 发布 2.5.1  →  tag v2.5.1   ✅
our-free-model 也要 2.5.1  →  tag v2.5.1   ❌ 已被占用，只能塞进加速器的 Release
                              → 资产挂在标题为「加速器 v2.5.1」的条目下，列表里根本找不到
```

因此**新发布的 Release 一律用 `<插件名>-v<版本>` 作为 tag**，各插件互不影响，版本号可以自由相同：

```
gh-accel-v2.5.1            → gh-accel 的 2.5.1
our-free-model-v2.5.1      → our-free-model 的 2.5.1   ← 同为 2.5.1，互不冲突
gh-accel-v2.6.1            → 加速器升到 2.6.1，与别的插件无关
our-free-model-v2.6.0      → OFM 自己走 2.6.0，不用管加速器到几
```

> **历史 tag 不迁移。** 2026-10-17 之前建的裸 `v<版本>` tag（`v1.0.0` … `v3.0.4`）保持原样、不删除不改名，已发布的安装链接继续可用。只有**新建**的 Release 走前缀格式；各插件 README 在下次同步时顺带换成前缀链接。

### ⚠️ 版本号三处必须一致（重点，2026-10-17 retry-count 教训）

同一插件的一次发布，**以下三处的版本号必须完全相同**，否则插件市场会误判：

| 位置 | 是什么 | 若不一致的后果 |
|---|---|---|
| `plugins/<插件名>/package.json` 的 `version` | 包内版本 | 装完市场显示旧版本，永远提示「有更新」→ 死循环 |
| Release 的 `tag`（去掉 `<插件名>-` 前缀和 `v`） | 发布版本 | 市场把 tag 当版本号，显示错乱 |
| 根 README 该插件段的徽章 `<code>v<版本></code>` | 文档版本 | 用户看到与实际不符 |

发布前用命令核对：`tar xzf <插件名>-plugin.tgz -O package/package.json | grep version` 必须等于 tag 的版本部分。

### ⚠️ 插件市场（dsh-jack-market）的识别规则

市场里的「市场 key」= **仓库 `plugins/` 下的目录名**，而「已安装检测」拿的是依赖名（npm 包名）。二者可能不同：

- 包名可能带 scope：`@local/gh-accel` → 市场 key `gh-accel`；
- 包名可能带 `dsh-` 前缀：`dsh-our-free-model` → 市场 key `our-free-model`；
- 也可能完全一致：`dsh-jack-market` → `dsh-jack-market`。

**新插件必须：目录名与 package.json 的 `name` 保持一致**（不带 scope、不带多余的 `dsh-` 前缀），这样市场识别零歧义。市场虽已兼容上述几种形态（2026-10-17 v0.4.0 起按候选 key 集合匹配），但兼容范围很窄——见下方「坑 2」，命名一致是硬约束而非建议。

### ⚠️ 常见坑（2026-10-20 按 dsh-jack-market 源码 + 本仓库真实数据逐条核对）

以下四条是「文档没写、但市场代码会真实踩到」的边界，发布前必须过一遍：

**坑 1｜「插件名」= `plugins/` 下的目录名，不是显示名、不是中文名。**
市场的 key 完全取自目录名；而 Release 资产名又必须严格匹配 `^<key>-plugin\.tgz$`。所以一次发布的三个名字必须是**同一个字符串**：

- 目录：`plugins/<key>/` → key = `<key>`
- 资产：`<key>-plugin.tgz`
- tag：`<key>-v<版本>`

例：`plugins/dsh-plugin-wallpaper-engine/` → `dsh-plugin-wallpaper-engine-plugin.tgz` → tag `dsh-plugin-wallpaper-engine-v1.3.3`。

❌ 用「插件显示名」或中文名做前缀 → 资产名前缀对不上目录，市场里该插件会**整条不显示**（最坏情况）或显示成「未发布包」。

**坑 2｜目录名 = `name` 是硬约束（比原文的「建议」更强）。**
市场的「已安装」检测（`client.js` 的 `keyCandidates`）只做两条归一化：去掉 npm scope、去掉开头的 `dsh-`。

- ✅ 能认：`@local/gh-accel` → `gh-accel`；`dsh-our-free-model` → `{dsh-our-free-model, our-free-model}`
- ❌ 认不出：目录 `jack-market` 而包名 `dsh-jack-market-skin`（多一段后缀）→ **永远显示「未安装」，装完仍是「安装」按钮**

因此新插件请让目录名与 `name` **完全一致**（不带 scope、不带多余的 `dsh-`）。

**坑 3｜tag 版本解析是「取末尾版本」，容错不代表可以乱写。**
`versionFromTag()` 只吃结尾的 `v?X.Y.Z[-pre]`，所以 `release-1.0.0` 也会被解析成 `1.0.0`。但市场同时要求资产名前缀 = 目录名——两套规则松紧不同，用非 `<key>-v<版本>` 的 tag 会出现「版本号看着有、插件却整条消失」的怪象，极难排查。

**tag 一律写 `<key>-v<版本>`**；也不要写 `v1.0`、`v1.0.0.0` 之类（解析结果为空串 → 市场显示无版本）。

**坑 4｜市场只取 `releases?per_page=100` 的前 100 条，插件越多越危险。**
市场为省匿名 API 配额，一次只拉 100 条 release。当前仓库共 58 条（gh-accel 17 + dsh-jack-market 15 + rea-tools 7 + …）尚安全，但继续增长后，**最早上架的老插件会被挤出这一页**：表现为「目录在、却显示未发布包、无法安装」。

发布节奏变快时，需把 `index.js` 的 `API_RELEASES` 改成分页拉取（或调大 `per_page`），否则老插件会陆续「失踪」。

> 附：目录下没有对应 release 资产时，市场**不会隐藏**该插件，而是照常列出并标成「未发布包」（按钮禁用）。
> 这是设计行为，用于提示「仓库里有、但还没发版」——不是 bug，无需修改。

## 二、同步 SOP（按顺序，缺一不可）

1. **改源码/修 bug**：`plugins/<插件名>/` 下；`node --check *.js` 语法、JSON 校验。
2. **版本号**：改 `plugins/<插件名>/package.json` 的 `version`。**该版本号必须等于本次 Release tag 的版本部分**（见上文「版本号三处一致」）。提交信息风格：
   - `feat(<名>): 说明，v旧 → v新` / `fix(<名>): ...` / `chore(<名>): 版本号 v旧 → v新`
3. **根 README.md（关键）**：该插件段落的简介 + 「vX.Y.Z 新增/修复」行；**两处安装链接**（「一条命令安装」代码块 + 「插件管理：添加插件」块）都改成 `<插件名>-v<新版本>/<插件名>-plugin.tgz`；新插件按注释里带占位模板做成的 `<details>` 折叠块插到列表末尾，折叠标题 `<summary>` 带版本号徽章（`<code>v<版本></code>`）。
4. **插件自带 README.md**（如有）：同步更新。
5. **提交**：`git add -A && git commit -m "<feat|fix|chore>(<名>): 说明，v旧 → v新"`。
6. **打包**：打成顶层 `package/` 的 tgz。**只含文件条目、不含目录条目**（用 `tar -T <(find <插件名> -type f | sort)` 并加 `--transform 's,^<插件名>,package,'`）；文件清单 = 插件目录内全部文件。打包后检查 `tar tzf` 第一层必须是 `package/`、且**没有以 `/` 结尾的目录条目**。
7. **发布 Release**：`tag = <插件名>-v<新版本>`（**必须带插件名前缀**，见上文 Tag 命名；此处 `<插件名>` 一律指 `plugins/` 下的**目录名**，见「坑 1」），`name = <插件显示名> v<新版本>`，target 指向 main 最新提交，上传 `<插件名>-plugin.tgz` 附件。
8. **复核**（逐项过，缺一不可）：
   - **三名字同一字符串**：`plugins/` 目录名 = `<插件名>-plugin.tgz` 的前缀 = tag 的 `<插件名>` 部分（见「坑 1」）；且目录名 = package.json 的 `name`（见「坑 2」）；
   - main 最新提交 sha 与本地一致、tree 一致；
   - tag 指向 = main 最新提交（或按需指向发布时提交）；
   - release 资产存在、上传者是仓库主人；
   - 实际下载 tgz，**sha256 与本地打包产物一致**，且 `tar xzf -O package/package.json` 的 `version` = tag 的版本部分。

> 本手机环境直连 github.com 不通：用 **GitHub Git Data API** 提交（blob → tree → commit → ref），`/repos/.../releases` 建 release，`uploads.github.com` 传附件。电脑上正常 `git push` 即可。
>
> **Git Data API 推送前必须确认 fast-forward**：本地父提交 sha 必须等于远端 main 当前 sha；不等则先 `git fetch` / 用 `--force=false` 的 PATCH，绝不强推覆盖他人提交。

## 三、可粘贴提示词（同步用）

> 我要把「<插件名>」<更新说明 / 新增插件> 同步到我的仓库 **Jack-kd/dsh-plugins**。请严格按 **docs/插件同步规范.md** 执行：
> 1. 在 `plugins/<插件名>/` 下改好源码（结构含 package.json / cordis.patch.yml / index.js / client.js），语法与 JSON 校验通过；
> 2. 把版本号升到 v<新版本>，并确保 **package.json 的 version = 本次 tag 的版本部分**（三处一致：package.json / tag / README 徽章）；
> 3. 更新根 README 安装速查段：简介说明 + 「v<新版本> 新增/修复」行 + **两处安装链接**都指向 `releases/download/<插件名>-v<新版本>/<插件名>-plugin.tgz`（新插件按注释占位模板做成 `<details>` 折叠块插到列表末尾，折叠标题带版本号徽章）；
> 4. 按仓库提交信息风格 commit：`feat/fix/chore(<插件名>): 说明，v<旧> → v<新>`；
> 5. 打包：插件目录打成顶层为 `package/` 的 `<插件名>-plugin.tgz`，**只含文件条目、不含目录条目**；
> 6. 建 Release：**tag = `<插件名>-v<新版本>`**，其中 `<插件名>` = `plugins/` 下的**目录名**（且目录名须等于 package.json 的 `name`、等于 tgz 名前缀，避免与其它插件顶号及市场认不出），target = main 最新提交，上传 tgz 附件；
> 7. 复核：**三名字同一字符串**（目录名 / tgz 名前缀 / tag 前缀）、main sha、tag 指向、release 资产、下载链接 **实际下载比对 sha256**、`tar xzf -O package/package.json` 的 version 与 tag 一致。
> （若环境直连 github.com 不通，用 GitHub Git Data API + uploads.github.com；**推送前先确认远端 main 等于本地父提交（fast-forward）**；README 记得写「升级需先卸载再装新版本」。）
